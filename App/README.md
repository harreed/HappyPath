# HappyPath

The workspace uses a single project and test tree with separate Past runs and Resources destinations. New tests open in goal mode: enter what the app should accomplish and, optionally, what a visible successful result looks like. Details opens the configuration inspector. Starting a run opens a live Simulator preview and a Summary/Details activity feed. The preview refreshes from Simulator screenshots during execution, while the completed recording is played from the saved run archive. Activity shows recorded events and explanations, not private model reasoning.

Resources stores reusable skill instructions in `resources.json` beside the project definition. Account and secret values are stored in macOS Keychain under the project identity and location; `resources.json` contains only names, types, and notes. Project export includes `resources.json` but never Keychain values. A copied or moved project needs credentials entered again. These resources can be managed here but are not yet injected into test steps automatically.

Build on macOS 27 with Xcode 27 selected using `sh Scripts/build_mac_app.sh`, then open `.build/HappyPath.app`. The app bundle has the identifier `dev.agentic.HappyPath`. To keep Keychain access approvals across rebuilds, put the SHA-1 fingerprint of a valid Apple Development signing identity (from `security find-identity -v -p codesigning`) in a local `.build-signing-identity` file at the repository root. The file is ignored by Git. `HAPPYPATH_SIGNING_IDENTITY` can override it for one build. Without either, the script uses an ad-hoc signature and Keychain may prompt again after each rebuild. Xcode can also open `Package.swift` for source debugging; use the packaged app for interactive validation because it includes the generic XCTest companion resource.

Create or open a `.uitestproject` from the home screen or File menu. Setup reads schemes, configurations and app products from Xcode; select an installed iOS Simulator. When changing a scheme or configuration, click Discover App Products before applying. Simulator discovery does not boot a device. Project Settings changes the configured target while retaining test identities. The generic companion is included in app resources and configured internally.

Sidebar context menus add suites/tests, rename, duplicate, delete and move items in canonical execution order. Save writes the validated immutable versioned definition to `project.json`. New/Open and closing/quitting protect pending edits. Source discovery and build errors remain visible.

Choose Replay steps on a test to use deterministic tap, type, swipe, wait, relaunch, assertion or Simulator control cards. Simulator controls can open deep links, set or clear location, change app permissions, or background and return to the app. Existing projects without a saved mode retain scripted behavior. Drag each card's left grip to reorder; the inspector edits targets, retry bounds, enabled state and breakpoints. Test Settings edits preconditions and final assertions. Draft Steps uses Claude through Apple's Foundation Models API when available, and keeps the generated plan separate until you explicitly append or replace reviewed blocks. The runner preserves scripted definitions when switching a test back to Follow a goal, but does not execute them in that mode.

Test Settings also configures each test's starting Simulator state: app data, app permissions, appearance and keychain. The default keeps the current state. Requested resets run after suite setup and can clear state that setup established; arrange setup accordingly when a test needs a clean start. Reinstalling removes the target app's local data, while keychain reset clears the selected Simulator's entire keychain.

The Run menu starts the selected test, selected set or all tests. Sidebar context menus run a suite/category or add tests to the selected set. Starting a run saves a validated definition and captures an immutable run snapshot. Only one run controls the Simulator at a time. Pause waits at a safe block boundary; Resume continues the same session, Step One Block advances one enabled block, and Stop retains evidence and awaits cleanup. Closing/quitting an active run keeps it open until Stop completes.

Run Results shows outcomes, timeline, screenshots and native video playback. Selecting a timeline event inspects its evidence; Return to Live resumes the current preview. Video seeks use the recorded startup anchor and show its timing uncertainty. Use This Target opens explicit review for updating an interaction block from a captured semantic node. In Run evidence, Add Visual Assertion from This Screenshot copies the latest preserved capture into the project and adds a local pixel comparison to the selected test. Visual comparison uses fixed thresholds and records the capture and image hashes. Send Screenshot to Claude for Analysis can answer a question about an archived screenshot after an explicit click; it sends that image to Anthropic and does not authorize runner actions or create an automated assertion. Save to retain reviewed edits.

Export Run copies the complete artifact directory, including visual references used in that run. Open Run can inspect a moved export independently of the source project; retry is disabled for unrelated imported archives. History's Retry This Snapshot creates a fresh run with the original snapshot. Run evidence also includes a bounded Simulator device log and matching crash reports when available. Network traces are not captured. SwiftData indexes metadata only; canonical definitions, ordered events, screenshots, raw snapshots, logs and video remain files.

Recovery Settings edits exact project-reviewed app alerts and project defaults. Test Settings chooses explicit inheritance or a test override, OCR fallback, budgets, the candidate chooser, and final goal evidence mode. Nonempty goals are assessed from final accessibility or OCR text; empty goals use deterministic assertions only. If text assessment needs pixels, an approved run checks a fresh screenshot with Clef, then Claude when needed. Without run-level approval or a valid image response, the goal needs review. SpringBoard alerts automatically select a unique visible accept action by default; Apple Account sign-in prompts are dismissed. Evidence inspection shows exact source captures, OCR boxes, candidate tables, goal citations and authoritative reasons. Model summaries are explanatory only. Stop bounds the caller; OS model workers may remain busy while unwinding.

Run `swift test` for the automated suite. The live planning probe is opt-in with `RUN_LIVE_APPLE_PLANNER=1 swift test --filter AuthoringTests.testLiveAppleTypedPlan`.
The live provider latency probe is opt-in with `RUN_LIVE_JEV_SPEED=1 swift test --filter JevSpeedTest.testJevLatency` and requires a configured credential.

Saved goal tests and Run → Run a Goal… use live navigation from a plain English outcome such as “Start a meditation”. An optional success description tells the final verifier exactly what visible state should prove completion. The runner observes each accessibility screen, asks the Apple goal navigator to choose one locally permitted control, records the action and a fresh result capture, then chooses again. It stops after the test's time limit or 80 actions. A second, source-bound assessment must verify the goal and success description before the run can pass. After a saved goal test passes that independent assessment, straightforward app-control taps can be stored as a verified route in local Application Support. A later run replays only while each screen and a unique safe control still match; it returns to live navigation on a mismatch and assesses the final goal again. Recovery, exploration, Apple sheets and approval steps are not stored as replay routes. Paywall purchases, account creation and consent are excluded from automatic candidates. Only exact known optional Apple Account and notification prompts can be dismissed; other system permission decisions and unknown screens require review. Navigation uses accessibility and OCR text; screenshot assessment is limited to final verification after explicit approval for that run.

The app uses Apple models for planning, goal navigation, final text assessment and summaries. Accessibility evidence comes first; if it cannot verify a goal, the runner tries local OCR. When screenshot evidence is needed and approved for that run, Clef-Flash checks the fresh image through Cloudflare Workers AI at a 0.4 confidence floor. Claude Haiku 5.5 checks the same capture if Clef is uncertain, below that floor or unavailable. An explicit image requirement goes directly to the image tier. Add Cloudflare and Claude credentials in Project Recovery Settings → Provider roles and runtime availability; they are stored in the local Keychain, never in project files. The opt-in resets after launch or retry. Remote image calls require network access and may incur API charges.
